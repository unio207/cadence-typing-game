# Make cadence's boundaries feel as good as its core

The notes point to one answer. A game feels satisfying when every action produces a clear, immediate, readable result. Bigger events get bigger responses. The feedback should scale with how well the player did, and restarting should cost seconds. Cadence already gets the moment-to-moment loop mostly right. Its caret and scroll springs (time constants of about 111 ms and 71 ms) sit inside the 85 to 150 ms range Monkeytype ships, and the drying ink is a clever way to make the page itself the HUD. Where cadence falls short is at the run boundaries and the big events. A death cuts straight to the result screen on the same frame, and a player still typing will very likely skip that screen. Clearing a goal, the game's only progression moment, gets just a HUD label change. Strikes, finished words and combo get almost no visible response. So the first edits should give the big moments (death, goal step-up, strike, finished word) short, on-style ink and typography motion, add 125 to 300 ms transitions between screens, and tie the look of the text to rhythm so the feedback depends on success. Scoring, stats and meta changes matter less, and sound should stay an optional, off-by-default flag because design principle 4 rules it out. Three probable bugs come first: the skipped result screen, an orphaned CSS line that probably deletes the `#rail` rule, and reduced-motion support that only reaches CSS.

## Fix these three bugs before any polish

**The result screen gets skipped on death.** Any `[a-z]` or space on a non-run screen calls `startRun()` and feeds that key into the new run ([src/shell.js:282-289](../src/shell.js)). Only `c` is caught first ([src/shell.js:276-280](../src/shell.js)). A `'strikes'` death is triggered by a keystroke, and at 100+ wpm the next keydown arrives roughly 60 to 120 ms later, so the result screen can disappear after a single frame. This conclusion comes from reading the code path. Nobody has watched it happen in a browser (cadence_codebase.md, sections 1 and 8). The fix: on the result screen, letters and space no longer start a run. Only Tab (already instant from anywhere, [src/shell.js:262](../src/shell.js)) and Enter restart. This keeps the spec's promise that "the result screen is never a gate" ([docs/superpowers/specs/2026-10-01-cadence-typing-game-design.md:41-42](../docs/superpowers/specs/2026-10-01-cadence-typing-game-design.md)), because restarting still takes one key. A related problem: starting from the title with a letter spends that letter as keystroke one against text the player has not seen yet ([src/shell.js:285-287](../src/shell.js)). Dropping the feed so the starting key only starts the run is a one-line change. Size: S.

**An orphaned CSS line probably drops the rail rule.** Commit 5ad6141 removed the `.branch` selector but left its body, `letter-spacing: -.01em; color: var(--ink); display: none; }`, at [index.html:123](../index.html). I confirmed that line is still there in this session. Under CSS parsing, a top-level rule's prelude swallows tokens up to the next `{`, so the `#rail { ... }` rule at [index.html:125](../index.html) likely ends up with an invalid selector and is thrown away. The canvas would then fall back to its default 300x150 placement. Delete line 123 and re-bundle `cadence.html` with `tools/bundle.js`. Nobody has checked this in devtools yet, and a ten-second look would confirm it. Size: S.

**Reduced motion only reaches CSS.** The media query at [index.html:204-206](../index.html) turns off CSS transitions and animations, but almost all of cadence's motion is JS-driven: the scroll and caret springs and the typing pulse ([src/render.js:41-51, 164-170](../src/render.js)). No file in `src/` calls `matchMedia`. The spec itself promises "`prefers-reduced-motion: reduce` sets springs to immediate" (design.md:188). WCAG 2.3.3 lists JS handling of the same preference (technique SCR40) as a way to meet the criterion, and points out that non-essential motion can cause dizziness and nausea ([W3C Understanding SC 2.3.3](https://www.w3.org/WAI/WCAG21/Understanding/animation-from-interactions)). Monkeytype's "off" caret setting (0 ms, instant) is an existing model ([monkeytype caret.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/elements/caret.ts)). The fix: read `matchMedia('(prefers-reduced-motion: reduce)')` once in render.js, set the springs to snap when it matches (`x = target`), and set `PULSE_MAX` to 0. Every animation proposed below should also go through this flag. Size: S. One more tiny fix while in there: the result hint "esc drafts" at [src/shell.js:243-244](../src/shell.js) refers to the draft chooser that 5ad6141 removed.

## Satisfaction comes from readable cause and effect, scaled to success

The frameworks in the notes agree more than their vocabulary suggests. Swink defines game feel as "real-time control of virtual objects in a simulated space, with interactions emphasised by polish" ([Wikipedia: Game feel](https://en.wikipedia.org/wiki/Game_feel)). Pichlmair and Johansen's survey of 200+ sources splits the craft into three parts: physicality (tuning), amplification (juicing, which signals how important each event is) and support (streamlining what the player is trying to do) ([arXiv 2011.09201](https://arxiv.org/abs/2011.09201)). Nijman's breakdown of one Nuclear Throne shot shows what amplification looks like when built: about ten small, numbered effects stacked on one input, including a **10 to 20 ms freeze on every hit** and a 1-frame white flash followed by a 2-frame hurt pose ([Infovore](https://infovore.org/?p=5275)). For a typing game, the important part is the principle underneath: response size should match event importance.

The controlled evidence adds a warning. Kao (2020) built four versions of the same game, and the medium and high juice versions beat both no juice and extreme juice on every measure ([summary](https://www.goodreads.com/author_blog_posts/19932694-the-effects-of-juiciness-in-an-action-rpg-new-study)). Kao et al.'s preregistered CHI '24 study (**n = 1,699**) found that plain amplification "unexpectedly decreased" effectance, competence and curiosity. Feedback that depended on success raised all three ([Imperial Spiral](https://spiral.imperial.ac.uk/entities/publication/253c32f5-d124-4a23-88b5-9aaaf114608d)). For cadence this is the most important design rule in the notes. The game's anti-juice stance ("No flashing, no shake, no sound", design.md:47-48) is partly backed by the evidence. Effects that fire the same way every time are a bad fit. Effects that get richer when the player types well are what the evidence supports.

Flow research points the same way. A meta-analysis of 28 studies found challenge-skill balance to be a **moderate** predictor of flow, with clear goals and a sense of control contributing alongside it ([Fong et al., via Institute of Coaching](https://www.instituteofcoaching.org/resources/challenge%E2%80%93skill-balance-and-antecedents-flow-meta-analytic-investigation)). Automatic difficulty adjustment improved performance in Robb and Zhang's n = 221 study but did not change enjoyment or flow ([CEEOL](https://ceeol.com/search/article-detail?id=1049985)). Chen argues that difficulty choices should be built into play, not asked between rounds. His between-round "faster/slower" prompt lengthened play but "broke the player's Flow" ([Chen thesis](https://www.jenovachen.com/flowingames/Flow_in_games_final.pdf)). Cadence's design already fits this: the goal ladder is picked on the title screen, and the ink is driven by the player's own speed.

Pacing and restart friction finish the picture. Designers describe a rising sawtooth: intensity climbs, broken by "shorter periods of falling intensity" and "brief windows of time where the player would have a chance to catch their breath" ([Game Developer, Craig Thomas](https://www.gamedeveloper.com/design/using-intensity-to-drive-player-engagement)). Left 4 Dead's Director lets things settle after intense stretches go on too long ([Game*Spark](https://www.gamespark.jp/article/2007/04/10/11866.html)). These are designer reports, and no controlled comparison exists. On restarts, McMillen's rule was that "the penalty for death basically turned into the amount of time you took to restart" ([Game Developer](https://www.gamedeveloper.com/game-platforms/-i-super-meat-boy-i-s-mcmillen-explains-why-so-hard-)). The counterpoint is that if the player is thrown back in after a couple of seconds, there is no time to understand the failure ([Screenwise](https://screenwiseapp.com/media/super-meat-boy-game)). Cadence needs both: an instant way out, and a death that lasts long enough to read. The goal-gradient effect is solid. People speed up as a visible goal gets close, and an illusion of progress speeds up completion ([Kivetz et al., JMR 2006](https://business.columbia.edu/sites/default/files-efs/pubfiles/1200/goalgradient.pdf)). That matters for cadence's "holding n/10" counter. SDT work adds that felt competence comes from "controls that were easily mastered" and "feedback that was clear and consistent" ([SDT.org PENS](https://selfdeterminationtheory.org/player-experience-of-needs-satisfaction-pens/)).

## Typing games reward the key and the word, not the screen

The typing precedents share a two-tier structure. Each keystroke gets a small, immediate, local response, and each finished word gets a larger one: the zombie explodes in Typing of the Dead, the laser hits in ZType, the world changes in Epistory ([Game Developer on Epistory](https://www.gamedeveloper.com/design/let-s-talk-about-epistory-typing-chronicles); [Chrome Unboxed on ZType](https://chromeunboxed.com/ztype-by-phoboslab-is-a-super-satisfying-way-to-kill-some-time-is-worth-a-try-for-the-whole-family/)). Cadence has the first tier (caret spring, pulse, rail tick, red error glyph). It has none of the second, because word completion is never detected (cadence_codebase.md, section 2).

Monkeytype is the closest model for a minimalist game, and its source gives exact numbers. The caret glides in **85 / 100 / 150 ms** (fast / medium default / slow) with a gentle `inOut(1.25)` ease. Each new key cancels the running animation. Line scroll and tape scroll take **125 ms**. A restart fades **125 ms out and 125 ms in**. The caret stops blinking and the mouse cursor is hidden while you type. Letter states are changes of colour only, with no default animation ([caret.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/elements/caret.ts); [test-ui.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/test/test-ui.ts); [focus.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/test/focus.ts); [test.scss](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/styles/test.scss)). The notes infer that its smoothness comes from one family of durations and one easing curve used everywhere, more than from any single effect. Combined with NN/g's guidance (about **100 ms** for direct feedback, **200 to 300 ms** for larger changes, ease-out for things arriving and ease-in for things leaving, and about **500 ms** "feels like a drag", per [NN/g](https://www.nngroup.com/articles/animation-duration/)), this gives cadence a timing vocabulary: roughly 100 to 150 ms for per-key and per-strike responses, 200 to 300 ms for screen changes, nothing near 500 ms, and the existing `--ease` curve `cubic-bezier(.33,1,.68,1)` ([index.html:38](../index.html)), which is already an ease-out.

The rhythm-game evidence and the typing data push in different directions. Rhythm games quantize what the player sees (Hi-Fi Rush lands attacks on the beat whatever the exact press time, per [GameAnim](https://www.gameanim.com/?p=106877)), and they build sound and visuals from sparse to full as the player succeeds (Tetris Effect, per [Retro Gamer](https://www.pressreader.com/uk/retro-gamer/20181228/281749860448812)). Typing, though, is not naturally even. In Dhakal et al.'s 136-million-keystroke study, fast typists averaged a **121.7 ms** inter-key interval, while bigram type alone moves the interval from **176 ms** (letter repeats) to **215 ms** (left-hand pairs) ([CHI 2018 paper](https://www.pokristensson.com/pubs/DhakalEtAlCHI2018.pdf)), and the first letter of each word is slower ([Crump et al. 2019](https://www.crumplab.com/publications/Crump/files/13615/Crump%20et%20al.%20-%202019%20-%20Instance%20theory%20predicts%20information%20theory%20Episo.pdf)). The notes found **no evidence** that typing to an imposed rhythm is faster or more accurate. This bears directly on cadence's rhythm score, discussed in the scoring section.

### 1. Hold the death long enough to read it (M)

Right now `finishRun()` runs on the death frame and `show('result')` cuts instantly ([src/shell.js:144-156](../src/shell.js)). The proposal is a short sequence. **Frame 0:** stop the springs and the pulse, and keep the ink exactly as it was, so the blind gap that killed the player stays on screen. That serves the spec's "every death is attributable" (design.md:43-46) and the fair-loss point from the flow notes. Mark the death glyph: the struck character for a `'strikes'` death, the caret character for `'dried'`. **Hold 400 ms**, then fade the run screen out over **200 ms ease-in** and the result in over **300 ms** with `--ease`. Total time is about 900 ms, under Nielsen's 1 s "flow of thought" limit ([NN/g response times](https://www.nngroup.com/articles/response-times-3-important-limits/)). Tab skips the whole sequence on any frame, so retrying still takes one key. The 200/300 ms durations and their easing directions are **[Sourced]** from [NN/g](https://www.nngroup.com/articles/animation-duration/). The idea that bigger events earn longer freezes is **[Sourced]** as a pattern ([critpoints](https://critpoints.net/2017/05/17/hitstophitfreezehitlaghitpausehitshit/); [Infovore](https://infovore.org/?p=5275)). The 400 ms hold is **[Inference]**: no source gives a death-pause length, and Nijman's 10 to 20 ms is for repeated hits, not a run ending. This edit together with the result-skip fix is the biggest flow gain on the list.

### 2. Fade between screens instead of hard cuts (S)

`.screen { display:none }` / `.is-active { display:block }` ([index.html:74-75](../index.html)) makes every change a cut. The proposal: keep `display` toggling for layout, but drive an opacity class. Screens arriving fade in over **250 ms** with `--ease` and screens leaving fade out over **200 ms** ease-in (title to run, result to title). For a Tab restart on the run screen, fade the new line in over **125 ms** and accept input from the first frame, so the spec's "retry in under 200 ms" (design.md:41-42) still holds even though the visual change takes longer. Values are **[Sourced]** from Monkeytype's 125 + 125 ms restart ([test-ui.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/test/test-ui.ts)) and NN/g's entry and exit guidance. One caution, **[Inference]**: `startRun()` measures the rail and char width only once the screen is visible ([src/shell.js:131-142](../src/shell.js)). Opacity 0 with `display:block` still allows that measurement, but `visibility:hidden` combined with `display:none` would not.

### 3. Turn the goal step-up into an event (M)

The step-up is the only progression moment, and today it is a HUD text swap from "holding 9/10" to "1 cleared" ([src/shell.js:179-185](../src/shell.js)). The proposal has two parts. **Holding:** swap the "holding n/10" text for a 1px hairline under the goal number that fills left to right over the 10 s hold (`HOLD_SECONDS`, [src/survival.js:83-88](../src/survival.js)). It pauses rather than resets on dips above 97%, matching `HOLD_RELEASE`. **[Sourced]**: the goal-gradient effect says a visible, filling target increases effort near the end ([Kivetz et al.](https://business.columbia.edu/sites/default/files-efs/pubfiles/1200/goalgradient.pdf)). **Clearing:** when `stepUp` fires ([src/draft-a.js:151-154](../src/draft-a.js)), set a one-shot flag the shell reads. The hairline holds full for 150 ms, then fades over 300 ms. The goal number counts up to the new rung over **300 ms** ease-out. The chapter label crossfades over 250 ms. The rail rule ([src/rail.js:117-147](../src/rail.js)) draws a single full-height tick in `--ink` at that moment. Nothing flashes or shakes, so this fits principle 4. Durations are **[Sourced]** as NN/g ranges, and the exact choreography is **[Inference]**. The pacing spec warns that the step-up could read as "a punishment rather than a promotion" (pacing.md:257-262). This edit is the cheapest way to make it read as a promotion before considering the bigger alternative of ending the run in success.

### 4. Give the player a breather after each clear (S, needs a balance run)

`stepUp` sets `from = value` (the old goal) and ramps to the next rung over 10 s ([src/survival.js:133-139](../src/survival.js)), so pressure never drops. The proposal is to set `from = 0.92 * value`. To show the effect: ratio = v / demand, so cutting demand by 8% multiplies the ratio by 1/0.92 ≈ 1.087. Because rising ratios apply instantly ([src/draft-a.js:146-150](../src/draft-a.js)), a player on goal at ratio 1.0 sees caret ink jump from baseInk(1.0) = (1.0 − 0.85)/0.5 = **0.30** to baseInk(1.087) = (1.087 − 0.85)/0.5 ≈ **0.47** on the same frame. The page visibly refills as the reward, and then the smoothstep ramp climbs back over 10 s. A short fall followed by a longer rise matches Thomas's "shorter periods of falling intensity" ([Game Developer](https://www.gamedeveloper.com/design/using-intensity-to-drive-player-engagement)), so the pattern is **[Sourced]**. The 0.92 value is **[Inference]**. Check it with `node tools/balance.js` against the README table before shipping, because it lengthens runs and changes the "10% over clears 1 to 2 levels" figures ([README.md:64-83](../README.md)).

### 5. Change the words when the level changes (M)

New chunks use the current chapter, but 200 to about 420 chars of old-chapter text are already buffered ([src/draft-a.js:27-28, 57-62](../src/draft-a.js)). That is roughly 25 to 50 s at 100 wpm, during which the HUD shows the new chapter and the hands still type the old one (cadence_codebase.md, section 4). The proposal: on step-up, truncate the generated text past the visible right edge and regenerate it from the new chapter. With the caret at 34% of a 1180px stage and 30px Plex Mono, I estimate about 45 visible characters ahead (**[Inference]**, not measured), which is about 5 s at 100 wpm. Truncating only past the visible edge keeps the swap off screen. The renderer's ring buffer keeps 110 chars ahead in the DOM ([src/render.js:4-6](../src/render.js)), so the out-of-view spans need re-rendering, which is what makes this M. The motivation is Koster's claim that fun is learning new patterns and boredom sets in once a pattern is mastered ([Koster, Theory of Fun 10 Years Later](https://www.raphkoster.com/wp-content/uploads/2026/07/Theory-of-Fun-10-Years-Later.pdf)). That is a **[Sourced]** designer opinion, and its link to typing texture is **[Inference]**.

### 6. Let strikes land (S)

The highest-stakes event gets the least motion: a strike dot just changes class to solid red ([index.html:92-94](../index.html), [src/shell.js:192-197](../src/shell.js)). The proposal: the spent dot animates `transform: scale(.4) → scale(1)` with its fill going from transparent to `--red` over **150 ms** `--ease`. The struck glyph gets a new `.strike` class: full-opacity red (stronger than `.err`'s .55, [index.html:107-109](../index.html)), on a small blob in the same `border-radius: 50% 40% 55% 45%` shape as the strike dots, scaling in from 0 over **120 ms** behind the glyph. That reads as an ink blot without glowing or moving any text. The "instant state change, then ease-out settle in 100 to 200 ms" shape is **[Sourced]**: NN/g's 100 ms feedback bound, and Nijman's flash-then-hold hit state (one white frame, then two hurt frames, about 33 + 67 ms at 30 fps, [Infovore](https://infovore.org/?p=5275)). The blot is **[Inference]**. The notes found no sourced craft for ink or brush effects, so its size and opacity are tuning choices, not research. design.md:169-173 says "nothing glows", which is why this uses a blob and not a `text-shadow` bleed.

### 7. Make the trail behind the caret a live record of rhythm (S to M)

The result page print already colours each char by its rhythm: opacity `0.18 + 0.82·(r/100)^1.9`, weight 500 when rhythm > 72 ([src/screens.js:78-104](../src/screens.js)). During play, typed chars just get flat `.done` ([src/render.js:147-150](../src/render.js)). The proposal: apply the same rule live to the 70 chars behind the caret, so steady stretches dry dark and medium-weight and ragged stretches dry pale. The line you leave behind becomes the HUD for rhythm, in the spirit of "the page is the HUD" (design.md:43-46). Plex Mono 500 is already loaded ([index.html:7-9](../index.html)), and a monospace face keeps the same advance width across weights, so nothing shifts. **[Sourced]**: success-dependent feedback beats uniform amplification ([Kao et al. CHI '24](https://spiral.imperial.ac.uk/entities/publication/253c32f5-d124-4a23-88b5-9aaaf114608d)), and Tetris Effect's audiovisual layer grows with success ([Retro Gamer](https://www.pressreader.com/uk/retro-gamer/20181228/281749860448812)). Writing the style once per typed char, at the moment the class changes, keeps it inside the renderer's one-write-per-keystroke budget ([src/render.js:4-39](../src/render.js)). That cost estimate is **[Inference]**.

### 8. Let finished words dry as a unit (M)

This adds the missing second tier. In `onKey` (around [src/draft-a.js:108-121](../src/draft-a.js)), detect a space that ends a word typed with no errors. The renderer then holds that word's glyphs at `--ink` for **60 ms** and dries them together to their done colour over **200 ms** ease-out, so words dry in chunks and not letter by letter. The rail gets a small notch on its 1px rule at that moment ([src/rail.js:117-147](../src/rail.js)). The text never moves, which protects the read-ahead. **[Sourced]**: the two-tier key/word pattern across ZType, Typing of the Dead and Epistory, and NN/g's 200 to 300 ms band for larger changes. **[Inference]**: the specific "dries as a unit" treatment and the 60 ms hold. Reward only clean words, so the feedback depends on success (Kao CHI '24).

### 9. Flash, then settle, on each typed glyph (S)

Spans are `transition: none` and `.done` applies instantly ([index.html:106](../index.html)). The proposal: the just-typed glyph shows `--ink` on the keystroke frame and eases to its done colour over **120 ms** ease-out, using `transition: color 120ms var(--ease)` on `.done` only. The first visible change still lands on the next frame, which keeps perceived latency at about one frame. **[Sourced]**: the 100 ms immediacy bound ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). **[Inference]**: the risk that recycled ring-buffer spans animate when their class is reset. Clear the transition when a span is reused. Monkeytype ships colour-only state changes with no animation by default, so this one is optional polish. If 7 and 8 land first, test whether it still adds anything.

### 10. Focus mode while typing (S)

Monkeytype hides the mouse cursor and stops the caret blink once typing starts, so everything that moves on screen is a response to a keystroke ([focus.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/test/focus.ts)). That part is **[Sourced]**. For cadence: set `cursor: none` on body while the run screen is active and the clock has started ([src/shell.js:131-142](../src/shell.js), [src/draft-a.js:91](../src/draft-a.js)), and restore it on mouse move. Optionally drop the HUD labels ([index.html:77](../index.html)) from `--mute` to `--faint` during play. The HUD currently shows score, wpm, demand, rhythm, goal, chapter and strikes ([index.html:83-94](../index.html)). The flow notes infer that one live number is enough during a run and that a full dashboard invites self-monitoring. That inference conflicts with how much information cadence shows, and quieting the labels is the low-risk version. **[Inference]**.

### 11. Count, don't tick (S)

The spec promised that score, wpm and rhythm "interpolate toward their true values" (design.md:185-186), but [src/shell.js:170-173](../src/shell.js) writes them directly. The proposal: `shown += (true − shown)·(1 − e^(−dt/0.1))`, a time constant of about **100 ms** matching the existing spring style ([src/render.js:165-170](../src/render.js)), and write `textContent` only when the rounded value changes. That also fixes the 6 to 8 unchanged writes per frame the codebase notes flag. The 100 ms comes from NN/g **[Sourced]**, and the choice of an exponential approach is **[Inference]**.

### 12. Leave the caret alone

`CARET_K = 9` gives a time constant of about 111 ms and `SCROLL_K = 14` about 71 ms ([src/render.js:7-8](../src/render.js)). Both sit inside Monkeytype's 85 to 150 ms caret family, and a spring that retargets every frame is interruptible by construction, which Monkeytype gets by cancelling tweens ([caret.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/elements/caret.ts)). The research supports the current tuning and the deliberate burst lag. The only change needed is the reduced-motion snap from the fix-first section.

## Scoring, stats and meta changes come second

**13. Show the result that matters without expanding (M).** The collapsed result screen shows duration, score and a record flag. Everything else sits behind "↓ all stats" ([src/screens.js:121-159](../src/screens.js)). The proposal: add one delta line ("+12 s vs your best at 100") and the last ~40 chars of the page print with the death glyph marked, both visible without expanding. **[Sourced]**: visible retrieval cues speed resumption after an interruption ([Hodgetts & Jones](https://orca.cardiff.ac.uk/id/eprint/33005/)), and detailed, unambiguous performance feedback supports competence ([Przybylski et al. 2009](https://selfdeterminationtheory.org/wp-content/uploads/2014/04/2009_PrzbylskiRyanRigby_PSPB-1.pdf)). Optionally restore the spec's hairline WPM-vs-demand strip (design.md:375-377). It was cut in 3220a4c because nothing read `wpmTrace` ([src/shell.js:220-250](../src/shell.js)), so it would need re-adding.

**14. Bank goals on mid-run Tab and Esc (S).** Tab and Esc discard the run without `bankGoals` ([src/shell.js:262-263](../src/shell.js)), so a goal held for 10 s and then abandoned is lost. Call `bankGoals(app.run)` before discarding if the clock had started. **[Inference]**. This is a fairness fix more than a reward.

**15. Per-goal bests and a suggested rung, shown but never asked (M).** Records are only `longest` and `highest` ([src/screens.js:51-63](../src/screens.js)). Store the best duration per goal in `cadence.goal.v1` ([src/shell.js:22-59](../src/shell.js)), show it next to the selected rung, and mark a suggested rung on the ladder (for example, the highest rung at or below the last run's average wpm). Keep it a marker, not a prompt: Chen's between-round prompt "broke the player's Flow" ([Chen thesis](https://www.jenovachen.com/flowingames/Flow_in_games_final.pdf)). Report closeness honestly ("0.8 wpm short") and never inflate it. In Finserås et al.'s game study, narrow losses produced **more boredom and less excitement** than a large win ([BORA](https://bora.uib.no/bora-xmlui/handle/1956/23601)).

**16. Make combo visible and let it soften instead of reset (S).** Combo drives up to a 2x multiplier ([src/metrics.js:80-85](../src/metrics.js)) but is never shown during the run. Show it as a small `×1.4` next to the score, and on a wrong key halve it (`combo = floor(combo/2)`) instead of zeroing it ([src/draft-a.js:116-121](../src/draft-a.js)). **[Inference]**, modelled on Duolingo's company-reported finding that softening streak loss with freezes raised activity ([Duolingo blog](https://blog.duolingo.com/how-duolingo-streak-builds-habit)). Note the tension with proposal 10. If the HUD is getting quieter, the combo could live in the trail (proposal 7) instead of as a number.

**17. Test whether the rhythm score punishes normal typing (M, investigate first).** Rhythm measures deviation over the last 16 per-keystroke intervals and reaches 0 at a normalized deviation of 0.35 ([src/metrics.js:4-40](../src/metrics.js)). Natural bigram timing alone spans 176 to 215 ms of mean interval across the population ([Dhakal et al.](https://www.pokristensson.com/pubs/DhakalEtAlCHI2018.pdf)). For a fast typist around 120 ms, a swing of 20 to 40 ms is roughly 15 to 35% of an interval. That suggests a typist with excellent control could still lose a lot of rhythm points to the motor system, not to any lack of skill. This is **[Inference]**: the per-person variability was not extracted, so it is a hypothesis to test. The cheap test is to give `tools/typist.js` bigram-dependent intervals and see where rhythm lands. If it is low, measure evenness per word or normalize by bigram class. Monkeytype's headline consistency is also coarse, using per-second raw WPM ([test-logic.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/test/test-logic.ts)). The pacing spec already names `DRY_TAU` as the dial if the goal turns out to be "a rhythm test as much as a speed test" (pacing.md:245-252).

**18. Optional sound, flagged and off by default (M).** Principle 4 rules out sound (design.md:47-48, README.md:5), so this is a proposal for a toggle, not for the core game. The evidence makes a strong case that sound tied to player actions is where minimalist games get most of their juice. Mini Metro's audio is "samples that are triggered in real-time as a result of player actions" ([Designing Sound](https://designingsound.org/2016/02/18/the-programmed-music-of-mini-metro-interview-with-rich-vreeland-disasterpeace)). Monkeytype ships a synthesized note mode: a sine oscillator, gain = volume/10, decaying with `setTargetAtTime(0, t, 0.3)`, plus a variant that walks a scale regardless of key ([sound-controller.ts](https://github.com/monkeytypegame/monkeytype/blob/master/frontend/src/ts/controllers/sound-controller.ts)). If built: use two "materials" for correct and error keys (Nijman, [Infovore](https://infovore.org/?p=5275)), play on keydown, and never let audio arrive before the visual. Audio early is detectable at about 45 ms, versus about 125 ms for audio late ([ITU-R BT.1359](https://itu.int/dms_pubrec/itu-r/rec/bt/R-REC-BT.1359-0-199802-S!!PDF-E.pdf)). Those figures come from speech clips, so they are only approximate for clicks. The notes found no sourced range for random pitch jitter and no sourced design for rising-pitch combos, so this report does not suggest values for either.

## What the research cannot tell you yet

Several gaps limit how far these proposals can be trusted. No study of game juice or feedback specific to typing games was found. No sourced craft numbers exist for ink, paint or brush effects, particle lifetimes or letter-by-letter text animation beyond Monkeytype's caret, so every ink-specific visual above (blot, drying as a unit, live page print) is design judgment. Pause durations for death or level-up have no source. Nothing was found on Alto's or Thumper's specific effects. No controlled study compares escalating-with-breathers pacing against a flat ramp, and nothing establishes an ideal run length for a typing game. Cadence has no real-player data. Every balance figure comes from the synthetic typist, and none of the visual claims about the current build (the rail bug, how the gradient looks in both themes, how long the result screen survives) were checked in a browser.

## Conclusion

The research shifts the question from "how much juice" to "where, and conditional on what". Cadence's restraint holds up against Kao's inverted-U and the CHI '24 finding, which together say uniform amplification is the wrong tool. The cost of that restraint has fallen on the boundaries and the big events, where a typing game earns most of its satisfaction: the death you should be able to read, the promotion that should feel like one, the word that should land. The proposals above add motion only where the player did something meaningful, and mostly in proportion to how well they did it. That keeps them inside the game's own rules (ink and typography, no shake, no glow, no forced sound).

One idea runs through the strongest proposals: the ink can carry more than survival. It already shows whether you are fast enough. Proposals 4, 7 and 8 let it also show whether you were steady and whether you just earned something, without adding a single HUD element. If only three things ship, make them the result-skip fix, the death beat and the live page-print trail, then play-test the step-up before touching scoring.
